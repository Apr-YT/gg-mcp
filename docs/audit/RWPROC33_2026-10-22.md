# rwproc33 驱动审计：全量搜索导致整机重启的根因与修复

- 日期：2026-10-22
- 对象：`Apr-YT/gg-rwproc33-driver`（本地工作副本 `build/rwProcMem33`，master @ `b0ce0ee`）
- 关联：`gg-mcp` 的 `agentd/driver.c`（PC 端唯一调用方）
- 起因：`docs/engineering/RWPROC33_ADAPTER.md §十二` 记录的未解决故障 —— rwproc 通道全量搜索
  `region=anonymous` 时设备重启，无 tombstone、pstore 为空，当时判断"根因在 KO 的 ioctl 实现里"

## 结论

`§十二` 的崩溃不是单一 bug，是**三道防线全部缺失后串起来的**。按触发顺序：

1. 物理地址合法性检查的上限算错了（`__pa()` 语义误用），所以它几乎不拦任何东西。
2. 页表遍历没判 PMD 大页，THP 区域的 pmd 被当成页表指针解引用。
3. 快路径拿 `__va()` 的结果直接 `virt_to_page()`，没有 `virt_addr_valid()` 兜底。
4. 整个遍历在 `mmap_lock` 之外，目标进程 munmap 会释放页表页（UAF）。

前三条任意一条都足以在内核态触发非法访存 → synchronous external abort → 整机重启。
第 2、3 条能解释"为什么与目标进程有关"：THP 与特殊映射的分布取决于进程的内存布局，
`pid 1` 这种小 footprint 进程很少命中，`sleep` / 游戏进程则必然命中。

**验证到哪一步了**：

| 层次 | 状态 | 证据 |
|---|---|---|
| arm64 交叉编译 | **通过** | WSL Ubuntu 24.04 + `crossbuild-essential-arm64` + **linux-6.12（vanilla 6.12.0）**，`make ARCH=arm64 M=... modules` 零编译错误，产出 `ELF 64-bit ARM aarch64` 的 `.ko`（rwProcMem 179KB / hwbp 140KB） |
| 新增分支确实进了产物 | **通过** | 带 `-DCONFIG_DEBUG_PRINTK` 重编后，`strings rwProcMem_module.ko` 里能查到 `pmd leaf: page=... paddr=...`、`pte not present`、`pte is special mapping`、`[rwfast] phys range invalid` |
| 真机运行 | **未做** | 无设备连接 |
| 6.12 GKI 特有差异 | **未验证** | 编译树是 vanilla 6.12.0（设备是 6.12.69 GKI），Xiaomi 改过的 `struct` 偏移、MODVERSIONS CRC 只能靠真机 |

编译树是 **vanilla linux-6.12.0**（不是 Ubuntu 打包的 6.8，也不是设备的 6.12.69 GKI）。
主版本对齐后，这一层能证明的是「语法、类型、API 存在性」——`pmd_leaf` / `virt_addr_valid` /
`mmap_read_lock` / `pfn_valid` 都在 6.12 头里，且代码确实编进了产物。
`SUBLEVEL` 差 69 个 stable 补丁，但这几个 API 在 6.12.x 内没有变化。
GKI 的 ABI 差异（`struct module` 真机 1600 字节、CRC）仍须真机。

**两次编译各抓到一个真实缺陷**：6.8 上暴露 `strscpy` 少传 size，6.12 上暴露
`snprintf` 源目标重叠（`-Wrestrict`）。这说明这份源码此前确实没在 vanilla 树上编过。

## 根因与证据

### R1 物理地址上限用错（`phy_mem_auto_offset.h:45`）

```c
si.totalram <<= bitcount;          /* 到这里 si.totalram 已经是「字节数」 */
g_phy_total_memory_size = __pa(si.totalram);
```

`__pa()` 的入参必须是**内核虚拟地址**。把一个 8GB 的字节数交给它，会走 `__phys_addr` 的
非线性地址分支，结果与物理地址空间无关（8GB 机器上算出约 10.7GB）。

于是 `check_phys_addr_valid_range(addr, count)`（`phy_mem.h:234`）变成：只要 `addr+count ≤ 10.7GB`
就放行。而 RAM 的物理地址不是从 0 连续排到 total_size 的 —— arm64 有 memstart 偏移、MMIO 空洞、
reserved 区，**total_size 以内完全可能存在非 RAM 地址**。这个检查因此形同虚设。

### R2 PMD 大页被当成页表页（`phy_mem.h:113` 起）

```c
pmd = pmd_offset(pud, virt_addr);
if (pmd_none(*pmd)) { goto out; }        /* 大页不是 none，直接通过 */
pte = pte_offset_kernel(pmd, virt_addr); /* ← pmd 值被当页表地址 */
```

THP 下 pmd 指向的是**页本身**，不是页表页。arm64 的 pmd 值里带 AF/SH/AttrIndx 等属性位，
`pte_offset_kernel()` 会算出非法地址并解引用。

### R3 快路径没有线性地址校验（`phy_mem_fast.h`，`CONFIG_ENABLE_FAST_PHYMEM` 默认开）

`fast_read_linear()` 对每个 `cur` 直接 `virt_to_page(cur)`。`__va(phy_addr)` 只做一次线性换算，
**不校验结果背后有没有 struct page**。phy 非法时 `(cur - PAGE_OFFSET) >> PAGE_SHIFT` 得到越界 pfn，
`pfn_to_page` 指向 vmemmap 之外，`kmap_local_page()` 读它 → abort。

慢路径至少有 `xlate_dev_mem_ptr()`（非 RAM 返回 NULL）挡一下，快路径什么都没有。

### R4 遍历在 mmap 锁外（`rwProcMem_module.c`）

`check_proc_map_can_read()` 里确实有 `down_read_mmap_lock()`，但它只包住"查 VMA"几行，
真正的 pte 遍历、force 路径的 `set_pte` 全在锁外。全量搜索耗时以分钟计，
目标进程 concurrent munmap 释放页表页后，我们继续解引用 pte。

### 附：顺手发现的两处

- `*out_pte` 在 `task`/`mm` 为空的两条提前 `return 0` 路径上没初始化。当前调用方在
  `phy_addr == 0` 时先 break，所以没爆；但这是个未初始化指针的隐患。
- `pte_none()` 不等于 `pte_present()`：被换出的页、`pte_special` 映射（`[vvar]`、MMIO、
  驱动的 remap 区）背后没有合法 struct page，`pte_page()` 拿到垃圾指针。

### 编译时暴露的真实缺陷：strscpy 少传参数

```c
strscpy(g_hide_dir_name, hide_dir_name);   /* 只有两个参数 */
```

`strscpy` 是函数，签名 `ssize_t strscpy(char *, const char *, size_t)`，三个参数缺一不可。
这行上面的注释写着「内核 strscpy 宏用 sizeof(dst)」—— 那个说法是错的，6.12 上照样
`too few arguments`。同一项目的 `hwBreakpointProc_module/hide_procfs_dir.h:69` 一直是
**三参正确写法**，两边不一致正好反证了这点。

它此前没被暴露，是因为 `RWPROC33_ADAPTER.md §十` 记着「禁用 hide_procfs_dir（置空该文件
+ 注释调用）」—— 那段时间这个文件没进编译；后来 `344f347` 把内容恢复了，错误也跟着回来，
但没人再编过一次。

修复只加了一个 `sizeof(g_hide_dir_name)`（数组 `[256]` 在同一个文件里可见），零行为变化。

### 编译时暴露的真实缺陷（二）：snprintf 源与目标重叠

```c
memset(entry->path, 0, sizeof(entry->path));
...
snprintf(entry->path, sizeof(entry->path), "%s[vdso]", entry->path);
```

源和目标同为 `entry->path`，违反 C 的 `restrict` 约定。6.12 的编译器对三处
（`[vdso]` / `[heap]` / `[stack]`）都报了 `-Wrestrict`。

它"碰巧"没出事，只因为上一行刚 `memset` 成空串，`%s` 读到首字节 0 就停了 ——
前缀本来就是空的，等价于直接写 `"[vdso]"`。修法是去掉自引用、写常量，行为完全一致，
同时不再违反编译器的无重叠优化假设（开了更激进的优化时这类代码可能真的读错）。

设计取舍，需要你确认：

1. **大页区域读不到了**。`*out_pte` 为 NULL 时，`force=1` 的改权限路径会因 `!pte` 放弃。
   当前 agentd 用 `force=0`（`driver.c:573` 明确禁用 force=1），所以只影响"能否读 THP 页"，
   不影响崩溃。要支持大页 force 得改 pmd 权限，风险比收益大，没做。
2. **`down_read_mmap_lock` 依赖 `mm_struct` 偏移自探测**。探测失败时返回非 0，我保留无锁行为
   （`lock_held=0`），不引入新故障但也修不好竞态。日志里 `found g_mmap_lock_offset` 能看出来。
3. **慢路径（关掉 `CONFIG_ENABLE_FAST_PHYMEM`）没动**。它靠 `xlate_dev_mem_ptr` 挡非法地址，
   但没有 `virt_addr_valid` 那种明确判据。当前开关是开的，不是崩溃点。

## 接口契约核对（这才是两个项目的真实集成点）

`agentd/driver.c` 通过 `/proc/<key>/<key>` 的 read() 协议与驱动交互。逐项核对：

| 契约 | agentd 侧 | 驱动侧 | 结论 |
|---|---|---|---|
| 请求头 33 字节 | `_Static_assert(sizeof(rwproc_request_t) == 33)` | `#pragma pack(1)` + `char` + 4×`uint64` | 一致 |
| 命中条目 312 字节 | `_Static_assert(... == 312)` | `task_id/hit_addr/hit_time` + `my_user_pt_regs`(288) | 一致 |
| init_device_info 1053 | `_Static_assert(... == 1053)` | `int+int+char[17]+char[1024]+int` = 1+4+4+17+1024+4（packed）| 一致 |
| 寄存器块 288 | `_Static_assert(... == 288)` | `regs[31]+sp+pc+pstate+orig_x0+syscallno` | 一致 |
| 命令码 1–12 | `RWBP_CMD_*` | `CMD_*`（显式 `= 1` 起始） | 一致 |
| 命令码 13 | `RWBP_CMD_INST_PROCESS_HWBP_ALL = 13`（**只定义，无任何调用**） | `CMD_INST_PROCESS_HWBP_ALL` | 定义一致，agentd 侧是死常量 |

尺寸类契约靠 4 条 `_Static_assert` 钉住，这一点做得好 —— 结构体一旦改动，agentd 编译就报错，
不会静默错位。本次只改内核内部实现，没碰任何结构体与命令码，**agentd 无需改动**。

## 本地版 vs GitHub 版：不能 merge，只能挑功能

`git merge-base` 返回空 —— 两边是无关历史，`git merge` 会让 259 个文件全部 add/add 冲突。
按文件名逐份比对内容后，真实差异是**功能互补**：

| 能力 | 本地（afei port） | GitHub（gg-ghost 线） |
|---|---|---|
| 物理内存快路径（`__va` + `kmap_local_page`） | 有（`phy_mem_fast.h`，`CONFIG_ENABLE_FAST_PHYMEM` 默认开） | **没有**（`fast_read_paddr` 出现 0 次，只走 `xlate_dev_mem_ptr` 慢路径） |
| 触摸注入（伪装 focaltech_ts + 抖动） | 没有 | 有（`rwProcMem_module.c` 内 78 处 touch/input_event） |
| 全线程断点 INST_ALL | 无（`RWBP_CMD_INST_PROCESS_HWBP_ALL` 是死常量） | 有（提交 `231012b`） |
| hwbp 四项缺陷修复 | 有（`4975327`） | 无 |
| CFI 运行时绕过 / anon channel | 有 | 无 |
| 6.12.69 CRC 表 + 内核资产 | 无 | 有（`kernel-assets/`，含 480k 行 kallsyms） |

**对本轮结论的影响**：

- R3（fast 路径无 `virt_addr_valid`）只存在于本地版。GitHub 版走慢路径，`xlate_dev_mem_ptr()`
  对非 RAM 返回 NULL，这一层它有自己的保护 —— 换句话说，**R3 是本地 fast 路径引入的回归**。
- R1（`__pa(si.totalram)`）与 R2（pmd 大页当页表页）**两版都有**。GitHub 版同样中招，
  只是慢路径减少了非法 phys 的暴露面，pmd 大页那条路一样会走到。

要合并只能手工挑：以本地为基线，把 GitHub 的触摸注入 / INST_ALL / kernel-assets 逐块移植，
再一起重编。这项工作会改动 `rwProcMem_module.c` 与 `hwBreakpointProc_module.c` 的大量逻辑，
建议单独一轮做，不要和崩溃修复混在一起。

## 怎么验证（剩下的是真机）

1. ~~arm64 交叉编译~~ —— 已完成，见上面的验证表。但**正式产物仍要用 `android16-6.12` 树重编**
   （`KERN_SRC=... bash scripts/build_rwproc_ko.sh`）：vanilla 6.12 只能证明语法与 API，
   GKI 的 `struct module` 尺寸（真机 1600 字节）与 MODVERSIONS CRC 必须用设备真值。
   复现本次验证环境（WSL）：
   ```bash
   apt-get install -y crossbuild-essential-arm64 bc bison flex libssl-dev libelf-dev
   # 源码：https://cdn.kernel.org/pub/linux/kernel/v6.x/linux-6.12.tar.xz
   #（HEAD 通但本机 GET 曾返回 0 字节，最后用的是本地已有的同一份 tar；重试或换镜像即可）
   mkdir -p /root/k612 && tar -xf linux-6.12.tar.xz -C /root/k612 --strip-components=1
   cd /root/k612 && make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- defconfig
   ./scripts/config --enable ANON_VMA_NAME     # 必须！关着会撞 static inline
   make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- syncconfig modules_prepare -j8
   make -C /root/k612 M=<模块目录> ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- KBUILD_MODPOST_WARN=1 modules
   ```
   两个必须的坑：
   - `ANON_VMA_NAME` 不做会报 `redefinition of 'anon_vma_name'` —— 未开启该 CONFIG 时内核头给
     `static inline` 桩，与代码里的 `__weak` 定义冲突；Android GKI 开着它，走函数声明分支，
     真机不存在这个冲突。**这是环境差异，不是源码缺陷。**
   - `modules_prepare` 不生成 `Module.symvers`，modpost 会报一片 undefined，必须
     `KBUILD_MODPOST_WARN=1`。这与代码正确性无关（`§10.4.1` 也记过空版本表仍能 insmod）。
2. **真机二分**：`gg_search_range` 逐区域推进，先 `sleep`（原崩溃目标），再缩小到具体 VMA：
   `[stack]`（易 THP）→ `[anon:dalvik-*]` → `[vvar]`/`[vdso]`。
   如果改成"读不到"而不是重启，就说明 R2/R3 命中。
3. **确认没修坏**：`gg_kernel_status` = `kernel-driver (kernel module)`；
   `gg_read_bytes` 读 init 的代码段；`gg_watch_set → poll → clear` 全流程。
4. `dmesg | grep -E "pmd leaf|invalid linear addr|pte is special"` 能直接看到走了哪条新分支。

## 真机验证（2026-10-22 20:2x，REDMI myron / 6.12.69-android16-6）

设备接上后做了第一次真机尝试。**结论：模块能加载、设备不崩、新守卫确实拦住了非法物理地址，
但读写链路本身还没打通**，所以「全量搜索不崩」这条尚未验证。

### 一、GKI 编译链打通了（关键突破）

上一节说「必须用完整 `android16-6.12` 树」，实际只需**头文件 + 设备 config**，
不必编 vmlinux：

```bash
# 源码：kernel_common android16-6.12（本地已有 249MB tarball，SUBLEVEL=52）
cd /root/gki
sed -i 's/^SUBLEVEL = 52/SUBLEVEL = 69/' Makefile      # 对齐设备 SUBLEVEL
./scripts/config --set-str LOCALVERSION "-android16-6-4k"   # 补上 -android16-6 前缀
cp device_config .config                                # 设备 /proc/config.gz
make ARCH=arm64 LLVM=1 CC=clang-18 olddefconfig syncconfig modules_prepare -j8
make -C /root/gki M=<模块目录> ARCH=arm64 LLVM=1 KBUILD_MODPOST_WARN=1 modules
```

结果：`this_module` 段 = **0x640 = 1600 字节**（与设备真值一致），
vermagic = `6.12.69-android16-6-4k SMP preempt mod_unload modversions aarch64`（逐字匹配）。

三个必须绕过的坑：

1. `No rule to make target 'protected_module_names_list'` —— GKI 的
   `CONFIG_MODULE_SIG_PROTECT_LIST` 直接当目标名用，构建脚本才会生成。造个空文件即可。
2. `rwProcMem_module.mod.c:28: expected expression` —— 无 `Module.symvers` 时 modpost 生成
   `__version_ext_names[] = ;`（§10.4.1 记过这个上游缺陷）。`build/ko/_dev/fix_modc.py` 修补。
3. `LLVM=1` 需要无版本后缀的 `clang`，Ubuntu 只给 `clang-18`，`ln -sf /usr/bin/clang-18 /usr/local/bin/clang`。

### 二、加载结果

- `insmod` RC=0，`/proc/e84523...` 节点就绪，dmesg 只有 `module hidden by default (init)`
- **设备零异常**：uptime 连续 6h16m 未重启，`dmesg | grep -cE "Oops|panic|BUG:|Unable to handle"` = **0**
- agentd 启动后 `driver self-test: UNAVAILABLE`，读写不可用

### 三、修没修好？日志给了肯定答案

`driver_self_test` 读自身地址 `0x5e43eff134` 时，dmesg 记录：

```
calc phy_addr:0x926afc134        ← 39.3 GB
pfn_sz:4
[rwfast] phys range invalid: 39303758132    ← 新守卫拦下
```

`0x926afc134` = 39,303,758,132，而设备 RAM 只有 11.6 GB（`si.totalram` 实测 11622510592）。

这正是 §十二 崩溃的触发条件：页表遍历给出一个不在 RAM 里的物理地址，旧代码接着
`__va()` → `virt_to_page()` → 越界 vmemmap → abort。现在被挡在 `fast_read_paddr` 的
`check_phys_addr_valid_range` / `virt_addr_valid` 处，**返回 0 而不是崩机**。

R1 的修复也在起作用：`g_phy_total_memory_size` 现在是真实的 11.6 GB（旧代码用
`__pa(bytes)` 会得到与物理地址空间无关的数，这个 39 GB 就会被放行）。

### 四、没打通的原因（与本次修复无关）

`pgd_index = 377` = `0x5e43eff134 >> 30`，说明该内核是 **3 级页表 + VA_BITS=39**，
配置与我的编译树完全一致（两边都是 `PGTABLE_LEVELS=3` / `ARM64_VA_BITS=39`），
所以偏移不是问题。设备 BTF 也确认了 `mm_struct` 布局：`task_size@96`、**`pgd@104`**、
`mmap_lock@136` —— 与模块编译期假设一致，`init_pgd_offset` 找到 TASK_SIZE 的位置也对。

也就是说 39 GB 是**页表项本身**给出的结果（某级 pte 指向了 RAM 之外的 pfn），
不是偏移算错。要定位到具体是哪一级、哪个 VMA，需要把 `get_proc_phy_addr` 的逐级
日志打开（已加 `printk_debug`），在真机上单地址复现。这一步没做完。

对照：设备上原有的 `rwProcMem_6.12.69.ko`（afei prebuilt，39 KB）之前跑过
`ITEST ALL PASS`，说明它的页表遍历在该内核上是通的 —— 本仓库这版 `AFEI port` 的
遍历路径与它可能有差异。这是下一步的入手点。

### 五、设备端实测到的其他事实

- `PROC_NODE_AUTH_KEY` = `e84523d7b60d5d341a7c4d1861773ecd`，与 `start_agentd.sh` 的
  `RWPROC_MEM_KEY` 一致；hwbp 模块未加载，`RWPROC_BP_KEY` 对应的节点不存在（预期）
- `dmesg` 里的 `%p` 已被内核 hash（`proc_pid_struct*:0x3bf5363b` 不是真指针），
  不要据此判断句柄被截断
- 设备 BTF 可导出：`adb exec-out "su -c 'cat /sys/kernel/btf/vmlinux'" > vmlinux.btf`，
  WSL 里 `pahole -C mm_struct vmlinux.btf` 直接查结构体偏移

## 真机验证结论（2026-10-22 20:4x 补完）

上面第三节说「39GB 是非法物理地址」——**那个判断是错的**，后续验证把它推翻了，特此更正。

### 一、39GB 是合法物理地址，不是垃圾值

用 `/proc/<pid>/pagemap` 从用户态独立核对同一个地址：

```
dd if=/proc/<pid>/pagemap bs=8 skip=$((0x5e43eff134>>12)) count=1 | od -t x8
→ 8100000000926afc        (bit63=present, pfn=0x926afc)
```

内核自己报的 pfn 就是 `0x926afc`（39.3GB），与 KO 算出的**完全一致**。也就是说：

- 页表遍历是对的（p4d/pud/pmd 的值都是合法页表项，末尾 `003` = VALID|TABLE）
- 设备 12GB RAM 但 **PA_BITS=48 的物理地址空间远大于 RAM 总量**，39GB 完全合法

**这直接否定了我先前「用 `si.totalram` 当物理地址上界」的修法**：totalram 是内核管理的
RAM 页总量（11.6GB），拿它当上界会把 39GB 这种合法页全部误拦 —— 表现正是
`[rwfast] phys range invalid` 之后读不到，`driver_self_test` 失败。

### 二、修正后的判据

`check_phys_addr_valid_range()` 现在只做整数回绕检查，**不再比较 totalram**：
合法性完全交给 `virt_addr_valid()`（快路径，内部即 pfn_valid）与
`xlate_dev_mem_ptr()`（慢路径，非 RAM 返回 NULL）。`g_phy_total_memory_size` 仅留作日志。

### 三、最终结果（这张表是结论）

| 验证项 | 结果 |
|---|---|
| `insmod`（GKI 树 + 设备 config + clang-18） | RC=0，`/proc/e84523...` 就绪 |
| `driver_self_test` | **channel OK (kernel-driver (rwproc33))** |
| `tests/integration/run_itest.ps1` | **ITEST ALL PASS**（search / read / write / freeze+unfreeze 全过；hwbp 未加载按预期 skip） |
| **全量匿名搜索：com.android.systemui（341MB RSS / 5940 VMA）** | **4.8s 完成，`truncated=false`（真扫完），设备不崩** |
| 设备稳定性 | uptime 连续，`dmesg \| grep -cE "Oops\|panic\|BUG:\|Unable to handle"` = **0** |

`truncated=false` 是关键：它不是「撞到结果上限提前返回」，而是把所有匿名区扫完后正常收尾。
这正是 §十二 里会让设备重启的操作，现在 4.8 秒跑完、设备零异常。

### 四、修复链条（说白了是哪一条起了作用）

旧代码 `g_phy_total_memory_size = __pa(si.totalram)` 在 arm64 上对「字节数」做 `__pa`，
结果是一个与物理地址空间无关的大数（远超真实 max_pfn），于是范围检查**放行一切** ——
非法 phys 直接进 `__va()` / `virt_to_page()`，碰到目标进程的特殊页就 abort。

现在：错误上限被移除，真正的判据是 `virt_addr_valid()`（每页检查，`fast_read_linear` 里）。
合法页（包括 39GB 那种）放行，非法 pfn 当场拦下返回 0。

systemui 那次全扫**没有触发任何守卫**（`dmesg | grep -c "phys range invalid|pte special|pmd leaf"` = 0）
—— 说明该进程的页表本来就正常，遍历正确即可完成。守卫是给异常页准备的，不是每次都用得上。

### 五、所谓「数字 value 被拒」不是 bug，是旧二进制没部署

先前记成遗留缺陷的那条，查清了：

```
{"value": "1234"}  → ok
{"value": 1234}    → bad value      ← 旧 gdm（2026-10-22 00:17）的行为
```

本地用项目自带的 `third_party/cJSON.c` 验证解析行为，完全正常：
`type=8`（Number）、`cJSON_IsNumber=1`、`valuedouble=1234`、`%.17g` → `"1234"`。

真正原因：**设备上的 `gdm` 是 00:17 编的，早于本轮对 `agentd/main.c` 的修改**，
旧版 `h_search` 直接取 `valuestring`（数字节点该字段恒为 NULL）→ 报 `bad value`。
本轮改完代码后只跑了 `run_itest.ps1`（它自带 itest 二进制，链接的是 `driver.c`），
**没有重新部署 gdm**，所以新模式一直没被真正测到。

部署新 gdm 后复测（systemui 5421）：

| 请求 | 结果 |
|---|---|
| `{"value":"1234"}` | count=1928, truncated=false, 4.74s |
| `{"value":1234}` | count=1928, truncated=false, 5.28s |
| `{"value":"0"}` / `{"value":0}` | 均 count=100000, truncated=true |
| `{"value":3735928559}` | count=1, truncated=false, 4.95s |
| `{"addr":"0x03984000"}` / `{"addr":60309504}` | 响应完全一致（都正确解析为同一地址） |

数字与字符串两条路结果逐项相同，地址参数的两种形式也一致 —— 本轮对
`j_scalar_str` / `j_addr_u64` 的改动在真机上生效。

**这条教训值得记下**：改完 agentd 必须重新部署 `gdm` 再测，
`run_itest.ps1` 绿了不代表设备上跑的 agentd 是新版。
