## A. 总体结论

**两个项目没有代码级集成。** 全仓 grep 双向无命中：gg-mcp 里搜不到 `ai-root` / 命名管道，
Ai-root 里搜不到 `gg-mcp` / MCP。它们是同一个 AI agent 的两个能力后端（一个管安卓内存，一个管
Windows 提权执行），共享的是"操作面"而非调用链。所以任务书里"Ai-root 调 gg-mcp"的模型不成立，
我没有编造这条链（详见 E 节）。

**gg-mcp**：核心链路（wire 帧、1MiB 上限、鉴权闸门、43 个工具分发）结构正确，基线单元测试全绿。
真正的问题是**参数类型约定在两端不一致**：PC 端把地址转成 `"0x..."` 字符串下发，agentd 的校验闸门
却"容忍 JSON 数字"，而所有 handler 又只按 `->valuestring` 取值 —— 数字节点该字段恒为 NULL，
于是 `gg_watch_inject` 一条数字参数就能让 root 守护进程段错误。同类不一致还表现为
`gg_write {value: 100}` 被误报"value required"（AI 客户端最常见的写法）。

**Ai-root**：策略引擎的"内置保护 → deny → allow → confirm → 默认"顺序与 fail-closed 骨架是真的，
令牌随机性与帧解析也经得起看。缺陷集中在**信任链的两端**：确认绑定的哈希输入是空格拼接的展示串
（批准 A 可执行 B）、`arg_forbid` 只做精确比较（`python -cprint(1)` 绕过内联脚本禁令）、
首次安装时 SID 静默写失败导致令牌对所有交互用户可读、以及安装失败时 fail-open 回退到用户可写目录。

已修 20 项（gg-mcp 9 / Ai-root 11）。未修的按风险列在 B 节末尾，其中 3 项需要真机或提权环境确认。

**验证到什么程度**：

| 项目 | 编译 | 单元测试 | 真实端到端 |
|---|---|---|---|
| gg-mcp | PC + agentd 均通过 | 13 个测试程序全过 + 3 道结构护栏 | **没有**：`adb devices` 无设备，设备端改动未上真机 |
| Ai-root | 通过，clippy 0 警告 | 185 passed（基线 178） | **有**：真实命名管道，`run whoami` → 确认 → 批准 → 重放执行成功 |

## E. 集成兼容性

**真实关系**：两个项目之间没有 IPC、没有共享配置、没有共同协议。可验证的耦合只有三条，都在部署/运维层：

1. **权限层**：Ai-root 让 AI 以 LocalSystem 执行命令，这正是跑 `gg-mcp` 的 `deploy.ps1`/`deploy_device.sh`
   （需要 adb、写 `/data/adb`、加载 KO）所缺的那层权限。两者是"上下游能力"关系，不是调用关系。
2. **信任传播**：Ai-root 的令牌一旦泄漏，攻击者可借它以 SYSTEM 执行 `adb` 与部署脚本，进而落到 gg-mcp
   的设备面。所以 AR-01（令牌对所有交互用户可读）与 AR-06（管道可被抢占）实际上也是 gg-mcp 的风险。
3. **共同的审计缺口**：gg-mcp 的 `gg_shell` 与 Ai-root 的 `run shell` 都能执行命令，两边的日志格式、
   留存位置、脱敏规则各写各的，跨系统追踪一次操作需要人工对时。没有统一的关联 id。

**已确认兼容**：无接口需要兼容（没有接口）。

**已修复的不匹配**：无跨项目接口不匹配可修——这条本身是结论，不是遗漏。

**仍存在的集成风险**：

- 本机存在多个 AI-Root 实例时（真实服务 + 前台 `server`），客户端连到哪个实例由命名管道分配决定，
  任务会被随机执行在 SYSTEM 服务或当前用户的前台实例上。审计中实际踩到了这个现象（同一命令两次结果不同）。
  这是 AR-U 类问题（无单实例控制），未修。
- 若将来要让 Ai-root 直接驱动 gg-mcp，需要先定义：谁持有 wire_key、谁负责 adb forward 生命周期、
  两侧错误码如何映射。现在这些都没有，不要假设它们"应该能通"。

1. **接真机跑 gg-mcp itest**（阻断项）。GG-01~09 全部只有编译级验证。特别是 GG-01/GG-02 的崩溃修复，
   需要在设备上用数字地址发一次 `gg_watch_inject` 与 `gg_set_results` 才算闭环。

## 2026-10-22 晚追加修复（真机验证）

设备接上后补做的两条，均已部署并在 6.12.69 真机上验证。

### GG-U1 shell 无超时 → 已修

`cmd_shell.c` 里 `read()` 与 `waitpid(...,0)` 都没有超时，而 `dispatch` 是整段持
`g_eng.mtx` 的。现在两条等待路径都带 deadline（读用 `poll`，收尸用 `WNOHANG` 轮询），
超时 `SIGKILL` 并返回 `GGERR_TIMEOUT`，错误信息里附已捕获的部分输出。

真机验证：

| 命令 | 结果 |
|---|---|
| `cat /dev/zero`（无限输出） | `code=7 TIMEOUT`，耗时 **10.0s** |
| 紧随其后的 `ping` | **0.040s** 返回（锁已释放，守护进程没死） |
| `id` / `getprop` / `ps -A` | 0.06–0.14s 正常返回 |

### 新发现（不在原清单里）：`--safe` / `--shell` / `--hwbp` 三个开关一直失效

修 GG-U1 时为了打开 shell 才发现：`main()` 里 `memset(&g_eng, 0, ...)` 在**参数解析之后**
（`main.c:2018` vs `1970`），而这三个开关是直接写 `g_eng` 字段的 —— 解析完立刻被清零。

| 开关 | 修复前 | 影响 |
|---|---|---|
| `--safe` | `safe_mode` 恒 0 | **只读保护形同虚设**：write/freeze/shell 全部放行 |
| `--shell` | `shell_enabled` 恒 0 | `gg_shell` 永远返回 `shell disabled` |
| `--hwbp` | `hwbp_allowed` 恒 0 | 硬件断点工具被拒 |

没被发现的原因：`hide_process()` 会清空 cmdline，从外部也看不出参数有没有生效。

修法：把 `memset` + `session_pid` + `result_cap` + `mutex_init` 前移到参数解析之前。
真机验证（带 `--safe` 启动）：

```
write  → code=13 SAFE_MODE
freeze → code=13 SAFE_MODE
shell  → code=13 SAFE_MODE
search → 正常放行（只读）
```

这条比 GG-U1 更该优先修 —— 它是**安全开关静默失效**，而表面行为完全正常。

### GG-U2（pid 复用）→ 已修，真机实测到真实复用

会话身份改为 (pid, starttime)。`process_starttime()` 读 `/proc/<pid>/stat` 第 22 字段；
解析前先找**最后一个** `')'` 再数字段，因为 comm 允许含空格与右括号（进程名由被调试方控制）。

三处消费：attach 记录、dispatch 每请求校验（`session_guard()`）、`freeze_loop` 每轮校验。
后两处的差别很重要 —— 冻结线程在后台持续写，用户不操作时它照样能改错进程。

真机两条分支都实测到：

```
# 目标退出
attach 27824（真实 starttime 182255）→ kill →
session self-heal: pid 27824 exited (starttime now=0 expected=182255)
read/search → code=3 NO_SESSION

# pid 真被复用（用 pidspin 反复 fork 直到新进程占住同一个号）
30420: sleep 900 (221527) → kill → 30420: pidspin (227844)
session self-heal: pid 30420 reused by another process (starttime now=227844 expected=221527)
read/write → code=3 NO_SESSION，没有碰那个无关进程
```

复现工具留在 `build/ko/_dev/pidspin.c`（已 gitignore）。要点：pid 分配是
「从 last_pid+1 找第一个空闲位」，所以绕一圈必然回到目标号；命中后子进程
`sleep(600)` 占住，父进程打印并退出。

### GG-U3（广播锁内阻塞）→ 已修，A/B 对比

先说测试方法的坑：**从 PC 侧测不出来**。`adb forward` 的本地进程会替客户端
读走数据，agentd 的发送缓冲永远填不满。必须让订阅端跑在**设备本地**且真的不读
（`build/ko/_dev/sub_stuck.c`，顺便把 `SO_RCVBUF` 压到 4KB 以便几个大事件就填满）。

A/B 结果（同一个不读订阅者 + 600KB 大事件广播）：

| | 旧实现（锁内 send） | 修复后（锁外 + dup + 1s 超时） |
|---|---|---|
| 触发阻塞的那条 relay | 10.25s | 2.10s |
| 同期**新连接** auth | **7.44s**（被拖住） | **0.01s** |

新连接被拖住是这条缺陷最狠的地方：`clients_register` 拿不到 `g_clients_mtx`，
于是"连得进 TCP、但一个请求都不处理"，从客户端看就是守护进程假死。

修复后的 2.1s 仍然存在，那是**订阅者自己那条请求**付的代价（600KB 分两次
`send()`，各等 1s 超时）。其他人完全不受影响。日志证据：

```
send failed fd=9 off=558521 len=600061 err=11 Try again
```

`fd=9` 是 `dup` 出来的副本（不是原连接 fd），`err=11` 即 `SO_SNDTIMEO` 到期，
`off=558521` 说明卡在 558KB 处 —— 接收窗口 4KB + 内核发送缓冲合计约这么大。

### GG-U6（cmd_end 丢 result）→ 已修

原实现：`snprintf(g_last_resp, 8192, "%s", s)` 截断后**仍按完整 JSON 解析**。
截断的串必然不是合法 JSON → parse 失败 → `result` 字段静默消失，订阅端看到的
`cmd_end` 与「handler 什么都没返回」完全一样。

实际影响面比标注的大：`gg_get_results limit=10000` 的响应实测 **510KB**，必然
走截断路径 —— 也就是说悬浮窗里这类命令**从来没显示过结果摘要**。

改法（逻辑抽到 `agentd/last_resp.h`，便于单测字节级行为）：

| 情况 | cmd_end 里的字段 |
|---|---|
| 未超长 | `result` = 完整对象（行为不变） |
| 超长 | `result_truncated: true`、`result_bytes: <原始长度>`、`result_preview: <前 256 字节>` |

预览截断点回退到 UTF-8 字符边界 —— 半个多字节字符会让下游 JSON 解析失败，
而这种问题在真机上几乎撞不到、撞到了也很难看出是这里。

真机验证（systemui 5421，`get_results` 响应 570030 字节）：

```
gg_get_results cmd_end 字段: [cmd, duration_ms, result_bytes, result_preview, result_truncated, success]
  success=true result_truncated=true result_bytes=510028 preview_len=256
普通响应(gg_search) cmd_end: result 是对象=True truncated=None
```

（510028 与 570030 的差是 cJSON 与 Python `json.dumps` 重新序列化的格式差异。）
