## A. 总体结论

**两个项目没有代码级集成。** 全仓 grep 双向无命中：gg-mcp 里搜不到 `ai-root` / 命名管道，
Ai-root 里搜不到 `gg-mcp` / MCP。它们是同一个 AI agent 的两个能力后端（一个管安卓内存，一个管
Windows 提权执行），共享的是"操作面"而非调用链。所以任务书里"Ai-root 调 gg-mcp"的模型不成立，
我没有编造这条链（详见 E 节）。

**gg-mcp**：核心链路（wire 帧、1MiB 上限、鉴权闸门、43 个工具分发）结构正确，基线单元测试全绿。
真正的问题是**参数类型约定在两端不一致**：PC 端把地址转成 `"0x..."` 字符串下发，agentd 的校验闸门
却"容忍 JSON 数字"，而所有 handler 又只按 `->valuestring` 取值 —— 数字节点该字段恒为 NULL，
于是 `gg_watch_inject` 一条数字参数就能让 root 守护进程段错误。同类不一致还表现为
`gg_write {value: 100}` 被误报"value required"（AI 客户端最常见的写法）。

**Ai-root**：策略引擎的"内置保护 → deny → allow → confirm → 默认"顺序与 fail-closed 骨架是真的，
令牌随机性与帧解析也经得起看。缺陷集中在**信任链的两端**：确认绑定的哈希输入是空格拼接的展示串
（批准 A 可执行 B）、`arg_forbid` 只做精确比较（`python -cprint(1)` 绕过内联脚本禁令）、
首次安装时 SID 静默写失败导致令牌对所有交互用户可读、以及安装失败时 fail-open 回退到用户可写目录。

已修 20 项（gg-mcp 9 / Ai-root 11）。未修的按风险列在 B 节末尾，其中 3 项需要真机或提权环境确认。

**验证到什么程度**：

| 项目 | 编译 | 单元测试 | 真实端到端 |
|---|---|---|---|
| gg-mcp | PC + agentd 均通过 | 13 个测试程序全过 + 3 道结构护栏 | **没有**：`adb devices` 无设备，设备端改动未上真机 |
| Ai-root | 通过，clippy 0 警告 | 185 passed（基线 178） | **有**：真实命名管道，`run whoami` → 确认 → 批准 → 重放执行成功 |

## E. 集成兼容性

**真实关系**：两个项目之间没有 IPC、没有共享配置、没有共同协议。可验证的耦合只有三条，都在部署/运维层：

1. **权限层**：Ai-root 让 AI 以 LocalSystem 执行命令，这正是跑 `gg-mcp` 的 `deploy.ps1`/`deploy_device.sh`
   （需要 adb、写 `/data/adb`、加载 KO）所缺的那层权限。两者是"上下游能力"关系，不是调用关系。
2. **信任传播**：Ai-root 的令牌一旦泄漏，攻击者可借它以 SYSTEM 执行 `adb` 与部署脚本，进而落到 gg-mcp
   的设备面。所以 AR-01（令牌对所有交互用户可读）与 AR-06（管道可被抢占）实际上也是 gg-mcp 的风险。
3. **共同的审计缺口**：gg-mcp 的 `gg_shell` 与 Ai-root 的 `run shell` 都能执行命令，两边的日志格式、
   留存位置、脱敏规则各写各的，跨系统追踪一次操作需要人工对时。没有统一的关联 id。

**已确认兼容**：无接口需要兼容（没有接口）。

**已修复的不匹配**：无跨项目接口不匹配可修——这条本身是结论，不是遗漏。

**仍存在的集成风险**：

- 本机存在多个 AI-Root 实例时（真实服务 + 前台 `server`），客户端连到哪个实例由命名管道分配决定，
  任务会被随机执行在 SYSTEM 服务或当前用户的前台实例上。审计中实际踩到了这个现象（同一命令两次结果不同）。
  这是 AR-U 类问题（无单实例控制），未修。
- 若将来要让 Ai-root 直接驱动 gg-mcp，需要先定义：谁持有 wire_key、谁负责 adb forward 生命周期、
  两侧错误码如何映射。现在这些都没有，不要假设它们"应该能通"。

## 2026-10-22 晚追加修复（真机验证）

设备接上后补做的两条，均已部署并在 6.12.69 真机上验证。

### GG-U1 shell 无超时 → 已修

`cmd_shell.c` 里 `read()` 与 `waitpid(...,0)` 都没有超时，而 `dispatch` 是整段持
`g_eng.mtx` 的。现在两条等待路径都带 deadline（读用 `poll`，收尸用 `WNOHANG` 轮询），
超时 `SIGKILL` 并返回 `GGERR_TIMEOUT`，错误信息里附已捕获的部分输出。

真机验证：

| 命令 | 结果 |
|---|---|
| `cat /dev/zero`（无限输出） | `code=7 TIMEOUT`，耗时 **10.0s** |
| 紧随其后的 `ping` | **0.040s** 返回（锁已释放，守护进程没死） |
| `id` / `getprop` / `ps -A` | 0.06–0.14s 正常返回 |

### 新发现（不在原清单里）：`--safe` / `--shell` / `--hwbp` 三个开关一直失效

修 GG-U1 时为了打开 shell 才发现：`main()` 里 `memset(&g_eng, 0, ...)` 在**参数解析之后**
（`main.c:2018` vs `1970`），而这三个开关是直接写 `g_eng` 字段的 —— 解析完立刻被清零。

| 开关 | 修复前 | 影响 |
|---|---|---|
| `--safe` | `safe_mode` 恒 0 | **只读保护形同虚设**：write/freeze/shell 全部放行 |
| `--shell` | `shell_enabled` 恒 0 | `gg_shell` 永远返回 `shell disabled` |
| `--hwbp` | `hwbp_allowed` 恒 0 | 硬件断点工具被拒 |

没被发现的原因：`hide_process()` 会清空 cmdline，从外部也看不出参数有没有生效。

修法：把 `memset` + `session_pid` + `result_cap` + `mutex_init` 前移到参数解析之前。
真机验证（带 `--safe` 启动）：

```
write  → code=13 SAFE_MODE
freeze → code=13 SAFE_MODE
shell  → code=13 SAFE_MODE
search → 正常放行（只读）
```

这条比 GG-U1 更该优先修 —— 它是**安全开关静默失效**，而表面行为完全正常。

### GG-U2（pid 复用）→ 已修，真机实测到真实复用

会话身份改为 (pid, starttime)。`process_starttime()` 读 `/proc/<pid>/stat` 第 22 字段；
解析前先找**最后一个** `')'` 再数字段，因为 comm 允许含空格与右括号（进程名由被调试方控制）。

三处消费：attach 记录、dispatch 每请求校验（`session_guard()`）、`freeze_loop` 每轮校验。
后两处的差别很重要 —— 冻结线程在后台持续写，用户不操作时它照样能改错进程。

真机两条分支都实测到：

```
# 目标退出
attach 27824（真实 starttime 182255）→ kill →
session self-heal: pid 27824 exited (starttime now=0 expected=182255)
read/search → code=3 NO_SESSION

# pid 真被复用（用 pidspin 反复 fork 直到新进程占住同一个号）
30420: sleep 900 (221527) → kill → 30420: pidspin (227844)
session self-heal: pid 30420 reused by another process (starttime now=227844 expected=221527)
read/write → code=3 NO_SESSION，没有碰那个无关进程
```

复现工具留在 `build/ko/_dev/pidspin.c`（已 gitignore）。要点：pid 分配是
「从 last_pid+1 找第一个空闲位」，所以绕一圈必然回到目标号；命中后子进程
`sleep(600)` 占住，父进程打印并退出。

### GG-U3（广播锁内阻塞）→ 已修，A/B 对比

先说测试方法的坑：**从 PC 侧测不出来**。`adb forward` 的本地进程会替客户端
读走数据，agentd 的发送缓冲永远填不满。必须让订阅端跑在**设备本地**且真的不读
（`build/ko/_dev/sub_stuck.c`，顺便把 `SO_RCVBUF` 压到 4KB 以便几个大事件就填满）。

A/B 结果（同一个不读订阅者 + 600KB 大事件广播）：

| | 旧实现（锁内 send） | 修复后（锁外 + dup + 1s 超时） |
|---|---|---|
| 触发阻塞的那条 relay | 10.25s | 2.10s |
| 同期**新连接** auth | **7.44s**（被拖住） | **0.01s** |

新连接被拖住是这条缺陷最狠的地方：`clients_register` 拿不到 `g_clients_mtx`，
于是"连得进 TCP、但一个请求都不处理"，从客户端看就是守护进程假死。

修复后的 2.1s 仍然存在，那是**订阅者自己那条请求**付的代价（600KB 分两次
`send()`，各等 1s 超时）。其他人完全不受影响。日志证据：

```
send failed fd=9 off=558521 len=600061 err=11 Try again
```

`fd=9` 是 `dup` 出来的副本（不是原连接 fd），`err=11` 即 `SO_SNDTIMEO` 到期，
`off=558521` 说明卡在 558KB 处 —— 接收窗口 4KB + 内核发送缓冲合计约这么大。

### GG-U6（cmd_end 丢 result）→ 已修

原实现：`snprintf(g_last_resp, 8192, "%s", s)` 截断后**仍按完整 JSON 解析**。
截断的串必然不是合法 JSON → parse 失败 → `result` 字段静默消失，订阅端看到的
`cmd_end` 与「handler 什么都没返回」完全一样。

实际影响面比标注的大：`gg_get_results limit=10000` 的响应实测 **510KB**，必然
走截断路径 —— 也就是说悬浮窗里这类命令**从来没显示过结果摘要**。

改法（逻辑抽到 `agentd/last_resp.h`，便于单测字节级行为）：

| 情况 | cmd_end 里的字段 |
|---|---|
| 未超长 | `result` = 完整对象（行为不变） |
| 超长 | `result_truncated: true`、`result_bytes: <原始长度>`、`result_preview: <前 256 字节>` |

预览截断点回退到 UTF-8 字符边界 —— 半个多字节字符会让下游 JSON 解析失败，
而这种问题在真机上几乎撞不到、撞到了也很难看出是这里。

真机验证（systemui 5421，`get_results` 响应 570030 字节）：

```
gg_get_results cmd_end 字段: [cmd, duration_ms, result_bytes, result_preview, result_truncated, success]
  success=true result_truncated=true result_bytes=510028 preview_len=256
普通响应(gg_search) cmd_end: result 是对象=True truncated=None
```

（510028 与 570030 的差是 cJSON 与 Python `json.dumps` 重新序列化的格式差异。）

### GG-U4（无 key 即放行）→ 已修

原实现：没有 `--wire-key` / `--wire-key-file` 时 AUTH **无条件成功**，只在启动
stderr 打一行 WARN。从客户端看握手是成功的，没人会去翻启动日志 —— 而 agentd
监听 `127.0.0.1:34127`，本机任意 App 都能连。

两种改法权衡：

| 方案 | 好处 | 代价 |
|---|---|---|
| 拒绝启动 | 最干净 | 手工调试不写部署脚本就起不来 |
| **生成临时密钥**（采纳） | 保留可用性，且没有"谁都能连"的窗口 | key 出现在启动日志里（日志在 `/data/adb/`，root only） |

实现要点：

- 16 字节 `/dev/urandom` → hex 32 字符
- 落盘 `/data/adb/GG-Ghost/wire.key.ephemeral`（0600，与正式 `wire.key` 分开），
  **下次启动优先复用** —— 否则每次重启 key 都变，客户端得跟着改
- `--wire-key-file` 指定了却读不出内容 → 仍然 FATAL。这里不能悄悄退化成临时 key，
  否则客户端拿的是另一份 key，报的是"鉴权失败"，真因藏在启动参数里
- 超长 key 从 `snprintf` 静默截断改为启动失败（截断后两边 key 不同，同样是
  难排查的鉴权失败）
- 成功响应带 `key_ephemeral` 标记

PC 端顺带修了一处从未生效的判断：`r.contains("r") && r["r"].value("auth_disabled")`
—— agentd 的响应是裸对象、没有外层 `"r"`，所以那条"agentd 关闭了鉴权"的警告
从来没打出来过。

真机验证（myron / 6.12.69）：

```
不带 key 启动 → 生成 a69821af…（32 字符），文件 0600 / 33 字节
临时 key AUTH  → {"authed":true,"key_ephemeral":true}
旧正式 key     → code=4 wire auth failed
不带 key       → code=4 wire auth failed     ← 原实现这里是 authed:true
空 key         → code=4 wire auth failed
重启（仍不带） → key 不变（复用落盘文件）
--wire-key-file 启动 → 64 字符 key 正常，AUTH 无 key_ephemeral
run_itest.ps1 → ITEST ALL PASS
```

**行为变更**：手工启动且不传 key 时，客户端必须换用日志里打印的临时 key。
正常部署（`start_agentd.sh` / `deploy.ps1` 都会传 `--wire-key-file`）不受影响。

**过程中发现的一个脚本缺口**（未改）：`start_agentd.sh` 的 `start` 在端口已被
别的实例占用时，新进程 bind 失败退出，但脚本仍打印"已启动" —— 它只按 pidfile
判断存活，而 pidfile 里可能是刚退出进程的号。手工 `setsid` 起过实例后忘了清理
就会踩到（本轮就踩了一次，误以为新版本没生效）。

### GG-U5（超限帧静默丢弃）→ 已修一半

原路径：`send_frame` 发现 `plen > GGWM_MAX_PAYLOAD` 就记一行日志返回 -1，
**什么帧都不发**。客户端只是"没收到响应"，一路等到连接层超时（PC 端 300s），
从外部看不出原因是"结果太大"。

改成 `send_ok` 序列化后先判上限（`gg_payload_fits()`，放 `wire_protocol.h`
双端可复用），超限则回 `GGERR_CAP` 错误帧，消息里带实际字节数、上限和修法。

**现状边界**：所有 handler 的输出都远低于 1MiB —— `get_results limit=10000`
实测 510028 字节，`hex_dump` 单次 256KB → 512KB。所以这条是给「将来加大 limit
或字段变长」留的兜底，正常路径不触发。

验证要造一个超限响应，但当前没有可构造路径，于是**临时把上限改成 64KB**
（只重编设备端，PC 端不动）：

```
正常（1MiB 上限）: get_results 10000 条 / 570030 字节 → flags=0x12，正常返回
超限（64KB 上限）: 同一请求 → 0.09s，flags=0x16，code=10
  "response too large: 510028 bytes exceeds the 65536-byte frame limit;
   reduce limit/len and page the results"
```

关键差别不是错误码，而是**0.09s vs 300s**。测完已恢复 1MiB 并重编部署
（`grep TEMP-CONTROL` 确认无残留）。

**仍未做**：协议分片。单帧 1MiB 是硬上限，余量 29%–42%，加 limit 前必须先分片。

## 2026-10-22 深夜：以《登山赛车》为靶场的实战

靶场：`com.fingersoft.hillclimb.noncmcc`（中国版，单进程 64 位），
路径 MCP(HTTP 8788) → adb forward → agentd → rwproc33 → 游戏进程。

### 打出来的缺陷（都已修）

| # | 缺陷 | 症状 | 根因 |
|---|---|---|---|
| 1 | `refine` 的 op 只认数字 | 任何 refine 后 `remaining` 直接 0，结果集被清空 | `->valueint` 对字符串节点恒为 0，而枚举从 1 开始 → 全部落到 switch default |
| 2 | 读不到的页不清位图 | `remaining` 卡在 5300 万，refine 形同虚设 | 失败只把快照填 0，位图不动 → 永久假候选 |
| 3 | attach 失败不清旧会话 | attach 报错后 read/search 仍"正常"，实际作用于上一个目标 | 失败分支直接 return，没动 session |
| 4 | 短读被当成读失败（修复 2 时自己引入的） | `unchanged` 归零，可读元素被误杀 | rwproc 遇不可读页是**短读**返回（64KB 只回 8KB），下一轮还能读到 |

第 1 条最隐蔽：走 MCP 时 PC 端会把 op norm 成数字，**碰巧正常**；只有直连
wire 的脚本会踩，而且表现只是"remaining 变 0"，看不出是参数没解析。

第 4 条值得记一下：修第 2 条时把「短读」和「完全读不到」混为一谈，结果
把可读元素清光了。定位靠的是在 refine 里加 `compared/kept` 计数 ——

### 新增：gg_search_undo

refine 是破坏性的，搜错一次只能重新 init（重读 256MB）。现在每次 refine 前
把位图存进环形栈（3 级，按需分配），可连续回退。只回退位图不回退数据快照。

真机（sleep 900，静态内存）：

```
init → 120832 候选
increased → 0
undo → 120832 (undone:true)
连续两次 refine 后 undo#1/#2 各回退一步，undo#3 报 "nothing to undo"
```

### 使用口径（本轮踩过的坑）

模糊搜索要在**数值稳定**的时刻 init。第一次实测时游戏还在跑，我直接
init + 立即 `increased`，得 0 —— 因为期间车已经撞停、值不再变化。
正确姿势：在菜单/暂停/操作间隙 init，再让目标发生一次明确变化后 refine。

### PC 端：agentd 重启后第一条请求必定失败 → 已修

现象：部署新 agentd 后，PC 端**下一条**命令必然报
`write to agentd failed (device offline?)`，再点一次就正常。
客户端手里还是旧 fd，第一次 send 失败后关 fd 置 -1，第二次调用才重连。

修法：发送失败时先重连、换新 seq 重放一次。

判据是**「整帧有没有发完」**，不是「一个字节都没发」：

- 实测 agentd 重启后，帧头那 20 字节往往还能塞进尚有余量的发送缓冲
  （send 成功），失败发生在 payload 阶段 —— 日志里是 `wr=-1`，不是"零字节"。
  只看零字节会漏掉这个最常见的情形（第一版就是这么写的，测出来没生效）。
- `wr==0`（整帧发出）绝不重放：对端可能已执行，重放会让 `gg_write` 做两次。
- `wr<0` 则对端连完整帧都拼不出来，不会执行。
- 只重放一次，且换新 seq。

真机：

```
重启 agentd → 立刻发一条命令（不重试）
  {"processes":[{"pid":22130,"name":"com.fingersoft.hillclimb.noncmcc",...}]}
  日志: [wire] write failed (wr=-1), reconnect and replay once
正常路径：连续 10 次 status 0.41s 全成功，attach/search 正常
run_itest.ps1 → ITEST ALL PASS
```

**调试备注**：服务端 wire 日志由 `GG_LOG_LEVEL` 控制（默认 2 = INFO）。
排查时用 `GG_LOG_LEVEL=1 ./gg-ghost-mcp.exe ... > mcp.log 2>&1`；
直接管道给 `tail` 会因为缓冲看不到实时输出（本轮先踩了这个，白查一轮）。

### GG-U5 分片 → 已完成

**为什么需要**：`gg_get_results limit=10000` 已经是 510KB，余量只剩 29%–42%。
放宽 limit 或给条目加字段就会越界，那时只剩"报错让调用方降 limit"一条路。

**协议**：新增 `GGWF_MORE`（0x0020）。同一响应的所有分片共用 seq，最后一片不带；
每片 ≤ 1MiB，接收端拼装总量 ≤ `GGWM_MAX_REASSEMBLED`（8MiB，防止对端一直发
MORE 帧把内存吃干）。

**能力协商**：客户端 AUTH 时带 `"frag":1` 才表示能重组，agentd 只看这个标记。
旧客户端不带 → 行为完全不变（超限仍回 `GGERR_CAP`）。这一步不能省：旧客户端
收到带 MORE 的帧会把第一片当完整响应解析，得到半个 JSON。

**两个实现细节，错了都不好查**：

1. **XOR 必须逐片独立做**。接收端是按帧解密的；整体加密后再切，第二片起的
   解密偏移全错，表现是 JSON 解析失败 —— 但你会以为是分片拼接错了。
2. **整组分片要在同一次发送锁持有期间发完**。中途被别的响应插进来，接收端
   按 seq 拼装就会错位。

**真机验证**（临时把上限压到 64KB，510028 字节的响应）：

```
新客户端（frag:1）  → 分 8 片 → 重组后 10000 条完整结果，0.10s
                    日志: send_ok: 510028 bytes > 65536, sending fragmented
旧客户端（不带 frag）→ flags=0x16, code=10, "response too large: 510028 bytes
                      exceeds the 65536-byte frame limit; ..."
恢复 1MiB          → 10000 条单帧 0.08s；itest ALL PASS；单测全绿
```
