## 一、为什么游戏要加密坐标

透视/自瞄的核心数据 = **实体坐标 + 视角矩阵**。对这两组数据加密 = 把 ESP 的门槛从"读内存"提到"逆向解密算法"。

加密强度分级（从弱到强）：

| 级别 | 形式 | 破解成本 |
|---|---|---|
| L0 | 明文（无保护） | 直接读 |
| L1 | 固定 key XOR / 字节反 | 脚本级（xor_search.py） |
| L2 | 地址相关 / 动态 key | 需逆向出解密函数 |
| L3 | 全写加密 + 全读解密 + 多副本（影子） | 需断点+反汇编，蜜罐风险 |
| L4 | 服务端加密下发（网络层） | 需破网络协议 |

## 二、7 种常见加密形式与识别特征

### 1. 简单 XOR（固定 key）
```c
pos.x = pos.x ^ 0xDEADBEEF;   // 或 ^ 0xFFFFFFFF（取反）、字节交换
```
**识别**：精确搜坐标值搜不到；用 `tools/xor_search.py` 对常用 key（0/0xFFFFFFFF/字节反/半字反/常见魔数）批量搜变体，命中即锁 key。

### 2. 地址相关加密（强，COD Warzone 实案）
```c
// 加密值 = f(存储地址, key)，key 每次访问还会更新
encrypted_float decrypt(uint64_t pointer, encrypted_float value, uint32_t key) {
    result.u32 = (((key ^ pointer) + 2) * (key ^ pointer)) ^ value.u32;
}
```
**关键**：解密需要**三元组**——加密值 + 存储地址 + key（key 字段本身也要读，且游戏访问时会 key1→key2 更新重加密）。
**识别**：同地址多次读值会变（key 在变）；字段旁有疑似 key 的伴生字段（+4/+8 处非坐标数值）。

### 3. 全写加密 + 全读解密（腾讯定制化对抗）
游戏**所有写坐标的地方先加密再存储，所有读的地方先解密再用**。
**识别**：断点命中"写矩阵/坐标"的 `str` 指令，但**存储前有额外算术链**（xor/add/mul 而非直接 mov）；读侧反汇编能看到对称的解密序列。

### 4. 隐式变换（非标准世界坐标）
坐标不以标准单位存：内部单位（厘米 vs 米）、加固定偏移、或旋转过的坐标系。
**识别**：值域异常（应 ±10k 却到 ±10^9，或全是大数）；但与真实坐标**线性相关**——采两组数据做差/比例即可还原。

### 5. 影子矩阵 / 多副本（干扰）
内存存在多份"矩阵"，只有一份是真的，其余是蜜罐或旧缓存。
**识别（真矩阵验证法）**：
- 视角转动时**只有真矩阵变**，影子矩阵不变
- 正交性检查：矩阵行向量正交（旋转矩阵性质）
- 尾行特征：标准 4x4 视图矩阵第 4 行 = `0,0,0,1`（或 0F 填充模式）

### 6. 服务端加密下发（网络层）
坐标由服务端加密（AES/Protobuf+签名）下发，客户端本地只有解密瞬间的明文。
**识别**：本地内存搜不到稳定的坐标明文；数据变化与网络包同步。
**对抗**：McDota 路线——拦截网络层解密（需破协议 schema + 动态字段映射），或行为层绕过。

### 7. 蜜罐假坐标（主动防御）
游戏在内存**故意放一份"完美但虚假"的坐标**，谁持续读它谁就是外挂（蜜罐特征：数值过于规整、永远领先真实位置一步、带隐藏标记字段）。
**识别**：对读到的坐标做**合法性交叉验证**（与物理规律/其他数据源对比），"太完美"的坐标警惕蜜罐。

## 三、对抗方法（按难度分级，外挂侧视角）

| # | 方法 | 原理 | 适用加密 | 备注 |
|---|---|---|---|---|
| A | **应用层复刻解密器** | 逆向出解密算法，外部自实现 | 1/2/3 全适用 | 最通用；Warzone 实案即此（读三元组外部算） |
| B | **hook 解密函数** | 内部注入，在解密输出处截明文 | 3（全读解密） | 需要内部注入能力 |
| C | **XMM/FPU 寄存器监控** | 解密后的浮点明文必经向量寄存器，采样寄存器拿明文 | 2/3/4 | 硬件断点（GG-Ghost 全线程 watch 可做） |
| D | **断点追写入者** | 断点命中写坐标的代码，观察存储前的算术链 → 反推加密算法 | 3 | 全线程断点 + 反汇编（我们的核心能力） |
| E | **行为层绕过** | 不碰加密坐标：屏幕识别（视觉）、网络包、或改读其他数据源 | 6/7 | 加密太强时的兜底 |
| F | **多副本交叉** | 影子矩阵场景：同时跟踪多副本，取"变化规律符合物理"的那个 | 5 | 真矩阵验证法 |

### 关键实操（Warzone 式加密的完整破解链）

```
1. 发现：精确搜视角角搜不到 → 怀疑加密
2. 断点：gg_watch_set 视角角地址（全线程）→ 操作视角 → 命中拿到写者 PC
3. 反汇编：gg_disassemble 命中区 → 看到加密序列（xor/key 运算）
4. 识别元组：反汇编确认需要 pointer/key/value 三个量
5. 读元组：gg_read 分别读 value、伴生 key 字段、记录地址
6. 复刻：外部实现 decrypt(pointer, value, key) → 明文
7. 验证：解出的值与屏幕实际视角对照（转视角 → 值变且正确）
```

## 四、防守方视角：它们怎么抓我们（检测面）

| 检测手段 | 原理 | 我们的暴露 | 规避 |
|---|---|---|---|
| **蜜罐** | 假坐标 + 读检测 | 持续读假坐标 = 暴露 | 合法性交叉验证；不迷信"完美"数据 |
| **行为分析** | 反应 <200ms / 视角 300°/s / 命中率 | 自瞄类特征 | 采样随机延迟（80-150ms）+ 平滑滤波 + 合理命中率 |
| **代码副本扫描** | 外挂自实现 W2S → 内存多份相似代码 AOB 可扫 | 纯外部实现无副本 | 外部实现天然无副本（优势） |
| **服务器锁步验证** | 客户端坐标 vs 服务端权威坐标对比 | 改坐标必露 | 只读不改坐标（透视不改数据） |
| **TracerPid** | 调试器检测 | 无（内核通道） | GG-Ghost 零 ptrace ✓ |

## 五、适配 GG-Ghost（我们的落点）

| 环节 | 用我们什么 |
|---|---|
| 判断是否加密 / 锁 key | `tools/xor_search.py`（14 key 变体批量搜 + 交叉收敛） |

## 六、使用边界（项目纪律，勿越）

- 网游/带反作弊游戏：**只读分析不修改**；坐标解密仅用于授权安全研究，不用于透视/自瞄实战
- 蜜罐识别是自保底线：读到"过于完美"的坐标先质疑再使用
- 行为层不要碰：采样随机化是底线（防行为画像），命中率/反应时间伪装不做
