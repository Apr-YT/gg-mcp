# 真实目标实践：登山赛车（Hill Climb Racing）

> 2026-10-23。第一个用**真实游戏**（非自建靶子）跑通的完整链路。
> 目标不是"改个数看看"，而是验证 gg-mcp 在真实商业游戏上能不能做到
> **定位 → 写入 → 被游戏接受 → 落盘 → 重启后仍生效**。
>
> 环境：设备 134d2f8，rwNova33 + rwNova 双 KO，agentd anon 通道，
> 游戏 `com.fingersoft.hillclimb.noncmcc`（pid 32369，arm64）。

## 分工

用户定调：**AI 主力 + 人辅助**。

- **AI**：attach、搜索、收敛候选、读写内存、截图 OCR、验证落盘
- **人**：在游戏里操作（进关卡跑一局、买东西/升级）、确认界面

这条边界很重要：AI 不去模拟游戏内点击（本轮试过 ghost_tap / `input tap`，
见"踩坑"），人也不用手工算地址。

## 完整链路

| # | 动作 | 执行方 | 数据 |
|---|---|---|---|
| 1 | 存档里确认币种字段 | AI | `hillclimbprefs.xml` → `<int name="coins" value="9670"/>` |
| 2 | 精确搜索 9670（dword / all） | AI | **56 条**命中，耗时 164ms |
| 3 | 进关卡跑一局 | 人 | 金币 9670 → **9775**，钻石 8 → 9 |
| 4 | 同址前后值求交集 | AI | 56 条 → **1 条**：`0x6d63982ed4` |
| 5 | 写 999999 | AI | 界面立刻显示 **999 999**（自动刷新，无需切页签） |
| 6 | 升级零件 | 人 | 花掉 957 000，剩 **42 999** |
| 7 | 游戏自动落盘 | 游戏 | `coins=42999`，XML mtime 13:21 |
| 8 | `am force-stop` + 重启 | AI | 界面仍 **42 999** ← 从存档读回 |

## 核心判据：同址前后值交集

单纯"搜新值"不够用：搜 9775 有 **45 条**噪音（关卡数据、计数器一堆同值）。

有效的是**跨时间、同地址**的约束：

```
集合 A = 值 = 9670 时的全部地址（56 条）
集合 B = 值 = 9775 时的全部地址（45 条）
A ∩ B = {0x6d63982ed4}      ← 一个地址的值从 A 值变成 B 值
```

为什么强：游戏里"某个地址的值恰好连续两次都等于你搜的数"概率极低，
而真变量必然**地址不变、值跟着变**。

这就是"模糊搜索 refine increased/decreased"的手工版 —— 但更灵活：
不需要提前建快照，只要人愿意制造一次变化。

> 注意方向：9670 → 9775 是**增加**，如果先建了模糊基线可以直接
> `refine increased`。本轮基线被 UI 的 attach 清掉了（见踩坑 3），
> 改用了地址集合求交。

## 踩坑

### 1. 界面数字有千位分隔，肉眼和 OCR 都会读错

界面是 `9 775`，用户转述成 "7775"，我第一次就照 7775 搜了 —— 80 条结果
全是噪音。截图放大确认后是 **9775**。

**对策**：读数值一律截图 + 裁剪局部 + OCR，不靠转述。

### 2. 批量写会把"哪条是真的"这个信息淹掉

第一次是 56 条候选里挑出 8 条可写地址（其余 48 条在只读页，`written=8 skipped=48`），
一起写 999999 —— 界面没变，于是判断"这些都不是"。

实际是 8 条里 7 条无关，**有效的那条被稀释了**，而且当时没确认界面是否
会自动刷新。后来单点写 `0x6d63982ed4` → 界面立刻变。

**对策**：候选 > 3 条时，先收敛（同址交集 / refine），再**单点**写验证。
批量写只用于"已确认同一个值的多处副本"。

### 3. UI 与 AI 共享一份全局结果集，UI 一 attach 就把 AI 的模糊基线清了

`g_eng.results` / `session_pid` 是 agentd 里的全局单例。AI 建完
`search_unknown_init`（67,108,864 个 dword），用户在 UI 里点了进程 attach，
结果集被 `session_drop` 清空 —— 再 `refine` 直接报 `refine failed (search first?)`。

**这是设计层面的耦合，不是 bug**（AGENTS 第 36 条已记录）。暂时靠约定避开：
**要建模糊基线时，先跟人说一声别在 UI 里 attach/搜索**。
真要同时用，得让 agentd 支持多结果集句柄（见 BACKLOG）。

### 4. 截图坐标不是 UI 坐标，别凭缩略图估

`screencap` 出来是 **2608x1200**，但看图工具展示时会缩放到 ~1080 宽，
按缩略图估的坐标换算回去偏几十像素 —— `ghost_tap` 全部打在按钮外面。
正确做法：`python scripts/find_button.py`（纯标准库解 PNG 找色块）或裁剪局部
（`scripts/crop_png.py`）后按真实像素定位。

**未定论**：修好坐标后 `input tap` / `ghost_tap` 在游戏内仍未触发界面变化，
同一时刻 `input keyevent 3`（Home）与桌面上的 `input swipe` 都正常。
说明输入注入链路本身是通的，问题在游戏接收侧（可能是 SurfaceView 的
TOUCH 事件分发或横屏坐标映射）。**没有再深挖** —— 按分工，游戏内操作归人。

## 可复用流程（换个游戏照抄）

```
0. 人能操作游戏、AI 能 attach
1. 存档/界面先确认目标字段的真实值和类型（XML/JSON 存档最好，直接看类型）
2. AI 精确搜当前值 → 记下地址集合 A（get_results 全量拉）
3. 人制造一次变化（赚/花/升级），AI 截图 OCR 确认新值 V'
4. AI 搜 V' → 集合 B；A ∩ B 通常收敛到个位数（本轮 56 → 1）
5. AI 单点写一个夸张值 → 人看界面是否变
6. 人正常消费一次（证明游戏逻辑接受这个值，不是只改了显示）
7. 读存档确认落盘 → AI 杀进程重启 → 界面值仍在新值 → 持久化成立
```

## 数据留档

| 项 | 值 |
|---|---|
| 游戏 | com.fingersoft.hillclimb.noncmcc（arm64） |
| 金币地址 | `0x6d63982ed4`（旧进程 32369）/ `0x6d63b09ed4`（新进程 28393） |
| 金币类型 | int32（存档 `<int>`，dword 搜索命中） |
| 搜索 56 条耗时 | 164ms（全内存 all） |
| 只读页占比 | 56 条中 48 条写不进（`skipped=48`），都是模块只读段 |
| 落盘验证 | `hillclimbprefs.xml` coins=42999，重启后界面一致 |

**注意尾号**：两个进程的金币地址尾号都是 `...ed4`，只有堆基址不同
（`0x6d63982ed4` vs `0x6d63b09ed4`，差 `0x188000`）。**说明对象内部布局稳定**，
变的是 ASLR 给堆的基址 —— 这正是"必须找基址 + 偏移"的理由。

## 定位基址（未完成，2026-10-23 设备离线中断）

### 已经确认的

1. `resolve_symbol(0x6d63b09ed4)` → `mapped=true, perms=rw-p, region=""`
   —— 纯匿名堆，**不属于任何模块**，所以没有"模块+偏移"这种直接答案。
2. 新进程结构布局与旧进程**完全一致**（都是 16 个 int32）：
   ```
   +0:1  +4:0  +8:0  +12:0  +16:0  +20:coins  +24:0
   +28:1 +32:1 +36:1 +40:1 +44:1 +48:3 +52:1 +56:0 +60:0
   ```
   即 **coins 在对象 `+0x14`**。
3. `pointer_scan(qword)` 找到 **3 个指向 coins 的容器**：
   `0x6ecb698cb8` / `0x6ecb6b2d38` / `0x6ecb6b7338`
   （三者的 `-8` 处正好也是 42999，所以是 `{int v; ptr p}` 结构，指针在 `+8`）
4. 对这三个容器**精确**搜 qword → **0 命中**。

### 对 0 命中的推断（未验证）

C++ 对象里存的几乎不会是"成员地址"，而是**对象首址**。coins 在 `+0x14`，
那么持有者存的应该是 `0x6d63b09ec0`（对象首址），而不是 `0x6d63b09ed4`。

`pointer_scan` 只做**精确相等**匹配，所以搜不到"指向对象任意成员"的指针 ——
这是工具的能力缺口，不是游戏的问题。

### 下一步（设备回来后照这个走）

```
1. gg_search_range min=0x6d63b09ec0 max=0x6d63b09f00 type=qword region=all
   → 找出所有"落在这个对象范围内"的指针（而不是精确等于 +0x14 的）
2. 对每个命中地址反推它属于哪个结构，再对其父结构首址做一次区间搜索
3. 重复直到命中地址落在 lib*.so 的 rw- 段（module 非空）
4. 最终得到 [libxxx.so+0xNNN] + 0x14 这种稳定路径
5. 重启游戏验证：基址 + 偏移能算回新的 coins 地址
```

### 两个实现问题（会挡住上面的流程）

1. **`pointer_scan` 只支持精确匹配**（`v == target`），无法表达"指向
   某区间的指针"。建议加 `range` 参数（目标 ± N 字节），一次抓出所有
   指向该对象的指针 —— 否则每换一个成员偏移就要重扫一遍全内存。
2. **`search_range` 的步进是 1 字节**（`agentd/search.c` mode 1 分支
   的 `for (... i++)`），不是 `i += sz`。后果：
   - 一个 8 字节指针落在区间内会被命中 **8 次**（i..i+7 的未对齐窗口都算）
   - 结果数虚高 8 倍，10 万条 cap 很快打满
   - 命中的地址是"未对齐窗口起点"，不是真实指针位置
   ARM64 指针天然 8 字节对齐，按 `sz` 步进既正确又快 8 倍。
   （exact 模式走 memchr 首字节预筛 + `i = off + 1`，不受影响。）

两条都**没动代码** —— 设备离线，改完无法验证，等设备回来一次做完。
